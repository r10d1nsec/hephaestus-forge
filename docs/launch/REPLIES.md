# Objection replies — comment cheat-sheet

Paste-ready answers for the common pushback on HN / X / Reddit. **Adapt the tone per platform**
(HN = plain, technical, no emoji; X = tighter; Reddit = native to the sub). Rules: be honest, never
defensive, concede real limitations, never ask for upvotes/stars in a reply. If you don't know, say so.

Links: repo `https://github.com/r10d1nsec/hephaestus-forge` · demo `https://r10d1nsec.github.io/hephaestus-forge/`

---

## 1. "How is this different from just asking ChatGPT/Claude to write a PRD?"

> You can absolutely ask an LLM "write me a PRD" — but you'll get a confident doc built on the
> assumptions *it* filled in for you. The value here isn't the generator, it's the **5-phase
> interview** that pulls the missing context out of *you* first (audience, frequency, constraints),
> and a **Solution-Fit phase** that decides the *kind* of solution — it'll tell you to build a
> 200-line automation instead of an app. Then it generates the pack from that transcript, locally,
> on the engine you already have. The spec is a side effect; the interview is the product.

## 2. "Why not just a system prompt / a custom GPT?"

> That was the v0 in my head too. Two things made it more than a prompt: (1) it keeps **state** —
> five phases, one sharp question per turn, the model decides when a phase is "done" — which a single
> prompt doesn't hold well; and (2) it's **engine-agnostic and local** — the same flow runs on your
> Claude Code CLI, Ollama, or any API, with the docs versioned and exportable as a ZIP. A custom GPT
> locks you to one vendor and sends your idea to their servers. This doesn't.

## 3. "Doesn't my coding agent (Claude Code/Cursor) already do this?"

> It can, if you drive it well — but it'll happily start *building* from a vague prompt, which is
> exactly the failure mode this exists to prevent. Forge sits one step earlier: it interviews you and
> hands your agent a sharp Blueprint + PRD + spec as context, so the agent builds the right thing the
> first time. It's not a competitor to your agent — it **runs on** your agent and feeds it.

## 4. "Privacy — does my idea/data leave my machine?"

> No. It's self-hosted: your idea, the interview transcript, and your API keys live in a local SQLite
> file. No telemetry, no account, no SaaS. If you use the Ollama or CLI engines it's fully offline;
> if you point it at an API provider, the only thing leaving is the prompt *to that provider you
> chose* — same as if you'd called them directly. Keys are never logged or returned by the API.

## 5. "Why another spec/PRD tool? The space is crowded."

> Fair — there are a few. The one thing none of them do is **Bring Your Own Engine**: run on the
> coding agents already in your PATH (Claude Code, Codex, Gemini CLI) or local Ollama, 100% local.
> The others are SaaS or lock you to one API. The second differentiator is the **solution-type
> recommendation** — it can tell you *not* to build the thing you came to spec. See the comparison
> table in the README if you want the honest side-by-side.

## 6. "LLM-generated specs are generic boilerplate."

> Often true when the input is one line and the model guesses the rest. The interview is the
> mitigation: by the time it generates, it has your answers on audience, frequency, scope and
> constraints, and the whole transcript goes into every doc. It won't beat a great human PM — the
> claim is narrower: it's a much better *starting point* than a cold prompt, and it stops you
> over-building. Real end-to-end output is in `examples/` (generated by the tool itself) — judge it
> there rather than taking my word.

## 7. "Isn't this just a wrapper around an LLM?"

> At the core, yes — it shells out to whatever engine you pick. I'm not claiming a new model. The
> work is in the **interview design** (the 5-phase prompts that decide what to ask and when a phase
> is done), the **engine abstraction** (one interface over CLI subprocess / Ollama / API), and the
> **Solution-Fit** logic. "Just a wrapper" is fair for a lot of AI tools; whether the wrapper earns
> its keep is the interview + local-first design. Try it and tell me if it doesn't.

## 8. Engine / technical questions

**"Can it use aider / opencode / <agent>?"**
> opencode landed already (`opencode run`). The contract a CLI engine needs is simply *prompt in →
> document text out on stdout*, so anything with a one-shot mode is a ~one-line addition. aider is a
> different shape — it's a repo *editor* that applies file edits, not a doc generator — so it'd need
> a different contract; I wrote up the reasoning as a non-goal in `docs/ENGINES.md`. PRs very welcome.

**"Why subprocess the CLIs instead of their APIs?"**
> So you can use the agent (and its auth/subscription) you *already have* without pasting another API
> key. It detects the binaries in your PATH and streams their stdout. Trade-off: CLI engines only
> work in **native mode** (`run.sh`) — the binaries live on your host, not in the Docker container.
> That's called out in the README.

**"CLI-only-in-native-mode is a weird limitation."**
> Agreed, it's a real constraint, not a feature. The binaries aren't in the container, so Docker mode
> covers API + Ollama and native mode unlocks the CLIs. Mounting the host binaries into the container
> is on the table if there's demand — open an issue.

**"What models/engines do you recommend for the interview?"**
> Honestly still gathering data — that's one of the things I'd love feedback on. Strong API models
> and the Claude Code CLI give the sharpest interviews; smaller local Ollama models work but ask
> blunter questions. If you try a local model and it interviews well, please report which one.

## 9. "How will you make money / will this last?"

> It's MIT and I'm not monetizing it right now — it's built in the open because I wanted it to exist
> and use it myself. No SaaS upsell, no telemetry. If it grows, sustainability is a real question I'd
> rather solve in the open with the community than pretend I've figured out. For now: it's yours,
> forkable, no strings.

## 10. Dismissive / low-effort negativity

> Keep it short and gracious; don't argue. "Fair — not everyone needs this. If you already nail your
> specs before prompting, you're past the problem it solves. Thanks for looking." Then move on.
