## Factores de riesgo

1. **外卖平台 API 是最大不确定性（决定性风险）。** 美团、饿了么等并不向个体小餐馆开放即插即用的开放 API：通常需要 ISV/服务商资质、商户逐家授权、上线审核，部分能力按行业或合作等级开放。若拿不到官方 API，唯一替代方案（抓取/模拟登录）既脆弱又触碰平台规则，不可作为正式方案。**这一项可能从"接 API"变成"先谈商务合作"，时间无法用工程估算覆盖。**
2. **多平台数据不一致。** 各平台订单字段、状态机、退款/改单逻辑、回调时序都不同，标准化与对账的工作量常被低估。
3. **AI 备货预测的冷启动问题。** 新店铺没有历史销量，预测在前 4–8 周几乎无效；需要规则兜底 + 逐步过渡，且预测准确度直接影响产品可信度（备货建议错一次，老板就不再信任）。
4. **目标用户为非技术人群。** 容错、引导、错误提示的设计成本高于一般 B 端工具，UI 返工概率大。
5. **微信小程序审核。** 涉及订单/经营数据，可能触发类目资质要求；审核驳回会拉长上线周期。
6. **库存模型的真实复杂度。** "一份菜=多种原料"的 BOM 扣减、共享原料、单位换算，比"加减库存数字"复杂得多。
7. **单一 LLM 提供商。** 降低了集成复杂度（好事），但形成单点依赖与成本/限流风险。

## Recomendaciones para reducir tiempo

1. **先验证 API 可得性，再写一行业务代码。** 用 1–2 周做平台接入的商务+技术可行性调研。这是决定项目能否成立的前置 Gate，不要并行开发。
2. **MVP 砍到单平台 + 手动录入。** 第一版只深度对接**一个**平台（覆盖率最高的那个），其余平台先做"手动/截图录入"占位，把 220 小时的接入风险降到约 80 小时。
3. **AI 备货建议先用规则引擎冒充。** v1 用"移动平均 + 星期/天气因子"的简单规则即可达到可用效果，LLM 留到有数据后再上，省下 30–60 小时且更稳。
4. **库存先用菜品级、不做原料 BOM。** 把原料级扣减引擎推迟到 v2，立刻砍掉 40–80 小时高风险工作。
5. **复用现成模板。** 微信登录、图表、日报导出用成熟组件/SDK，不自研。
6. **日报先只读、不导出。** 导出/多维筛选放到后续迭代。

> 采用上述裁剪后的"真·MVP"（单平台 + 规则备货 + 菜品级库存）可压缩到约 **180 – 300 小时**，全职 1 人约 **5 – 8 周**可上线验证，再用真实数据驱动后续投入。
